# Sprint 29 — Write Contract + Validation Plan

## 1. Purpose

Define the write contract before any real Supabase write operation is enabled.

Sprint 29 is a planning and interface-hardening sprint only. It defines future write payloads, validation expectations, allowed operations, failure behavior and adapter shape. It does not perform insert, update, delete, submit, Auth, RLS, schema or seed changes.

## 2. Non-goals

Sprint 29 does not implement real database writes.

Forbidden in this sprint:

- insert
- update
- delete
- real submit
- Auth
- CRUD
- RLS changes
- schema changes
- seed changes
- UI changes
- CSS changes
- route changes
- public form writes
- internal create writes

## 3. Allowed future write operations

The following operations are mapped for future implementation only.

Internal future operations:

1. create call
2. create kaddish request
3. create volunteer
4. create member

Public future operations:

5. submit public kaddish request
6. submit public minyan request
7. submit public volunteer join
8. submit donation interest / partner interest as interest-only submission

Later operational actions:

9. update status
10. add timeline note
11. assign volunteer
12. close request or call

## 4. Forbidden write operations for now

Until explicitly approved in a later sprint, the system must not perform:

- direct writes from pages
- write operations inside React components
- writes through read adapters
- public submissions
- status updates
- volunteer assignment writes
- activity log writes
- timeline note writes
- close or cancel actions
- donation/payment writes
- Auth-dependent writes

## 7. Server/generated fields

The following must be generated by the server/database/future write layer, not trusted from the client:

- entity IDs such as `callId`, `requestId`, `volunteerId`, `memberId`
- created timestamp
- updated timestamp
- initial status defaults
- audit metadata
- source tracking metadata when applicable
- assignment IDs
- activity log IDs

## 8. Client-provided fields

The client may provide only domain input fields intentionally collected in the relevant form:

- names
- phone
- email
- city
- date
- time
- request type
- urgency
- availability
- membership type
- public source marker for public payloads
- free text note only where explicitly supported

The client must not provide trusted operational fields such as final status, createdAt, updatedAt, assigned volunteer IDs or audit state unless explicitly approved in a later sprint.

## 9. Validation rules

General validation rules:

- Required strings must be non-empty after trimming.
- Phone fields must be present where required and must be normalized before write implementation.
- Email is required for member creation and optional for donation/interest payloads unless future policy changes.
- Enum values must come from existing TypeScript unions only.
- Date fields must be valid and normalized before persistence.
- Time fields must be valid and normalized before persistence.
- Unknown fields must be rejected rather than silently persisted.
- Public payloads must include an allowed `source` value.
- Internal and public payloads must remain separate.

## 10. Error handling model

Write operations must return `WriteResult<T>`.

Failure codes:

- `VALIDATION_ERROR`
- `DUPLICATE_SUSPECTED`
- `NETWORK_ERROR`
- `SUPABASE_NOT_CONFIGURED`
- `FORBIDDEN_OPERATION`
- `UNKNOWN_ERROR`

Rules:

- No page should assume a write succeeded without `ok: true`.
- Validation failures must identify a field where possible.
- Supabase/network failures must not create fake success states.
- Public submissions must not expose internal error details.
- Internal pages may show operationally useful errors later, subject to UI approval.

## 11. Duplicate prevention assumptions

Future duplicate prevention should check at least:

- public kaddish request: requester phone + deceased name + date
- public minyan request: phone/contact + city + time/date
- volunteer join: phone
- member: email and/or phone
- call: city + time + date or operational time window

Sprint 29 does not implement duplicate checks. It defines them as required before enabling writes.

## 12. Fallback/failure behavior

Before writes are enabled:

- All write adapter methods return `FORBIDDEN_OPERATION`.
- No database mutation occurs.
- No UI state should change as if persistence happened.
- No optimistic creation is allowed.
- No local-only fake success is allowed.

After future write approval:

- On validation failure, do not write.
- On Supabase failure, do not display success.
- On duplicate suspicion, block or require explicit review, depending on future policy.
- On public submission failure, keep the user-facing response safe and generic.

## 13. Audit/logging future notes

Future writes should eventually generate audit/activity records for:

- entity created
- status updated
- volunteer assigned
- timeline note added
- request/call closed
- public submission received
- public submission converted to internal entity

Sprint 29 does not implement audit writes because schema, RLS and write permissions are not approved yet.

## 14. Public submission rules

Public submissions must remain lower-trust than internal creates.

Future public submissions should:

- validate required fields
- store source
- avoid automatic operational completion
- avoid direct privileged actions
- avoid assigning volunteers automatically without approved logic
- avoid exposing internal IDs beyond public-safe tracking numbers
- avoid payment/donation processing unless separately approved

## 15. Internal create rules

Future internal create operations should:

- use typed payloads
- validate before write
- map payload into DB row shape through a write mapper or adapter layer
- generate default status safely
- return the mapped domain entity after successful persistence
- not write from pages directly
- not bypass the adapter

## 16. Open questions before Sprint 30

Before real writes begin, the architect must decide:

1. Which internal create action is the first write pilot?
2. Which fields are mandatory in each create form versus optional?
3. What are the canonical initial statuses for each entity?
4. Should public submissions write directly to entity tables or to `public_submissions` first?
5. What duplicate detection policy blocks writes versus flags review?
6. What audit events are mandatory for create operations?
7. What user-facing error messages are allowed?
8. Whether schema gaps require a dedicated schema sprint before Sprint 30.
9. Whether RLS/Auth must precede any write pilot.
10. Whether writes stay disabled in production until Auth hardening is complete.
